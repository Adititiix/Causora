# INC-2047: Replayed CDC events cause a duplicate key violation in load_shipments_fact

- **Date:** 2026-10-15
- **Severity:** SEV-3
- **Pipeline:** shipments_sync
- **Failed task:** load_shipments_fact
- **Duration:** 98 minutes (01:20 to 02:58 UTC)
- **Impact:** none downstream; shipments_fact was reloaded before the 03:30 finance_reporting freshness check

## Summary

On 2026-10-15 the load_shipments_fact task in shipments_sync failed with a UniqueViolation on shipments_fact_pkey. The transformed input held 594 duplicate rows. The load ran in one transaction, so nothing was written. After deduplication and a switch to an upsert, the load succeeded at 02:58.

## Timeline (UTC)

- 2026-10-14 22:10 logistics-eng restarted the fulfilment CDC connector, which resumed from its 21:40 checkpoint.
- 01:00 The scheduled shipments_sync run started; extract_shipments and transform_shipments succeeded.
- 01:20 load_shipments_fact failed with UniqueViolation; the transaction was rolled back.
- 01:36 On-call engineer acknowledged.
- 01:52 On-call found 594 duplicated shipment_id values in shipments_raw.
- 02:20 logistics-eng confirmed the connector restart and the replay from 21:40.
- 02:38 Fix deployed: deduplication in transform_shipments and an upsert in load_shipments_fact.
- 02:44 transform_shipments cleared; 02:58 load_shipments_fact succeeded (47,312 rows).
- 03:31 finance_reporting.check_source_freshness passed.

## Observed evidence

- Task log shipments_sync / load_shipments_fact / 2026-10-15: "Input has 47,906 rows but 47,312 distinct shipment_id values (594 duplicate rows)", then psycopg2.errors.UniqueViolation on constraint shipments_fact_pkey, Key (shipment_id)=(SHP-88412907), then "Transaction rolled back; 0 rows written". This was attempt 1 of 1.
- In shipments_raw, each of the 594 duplicated shipment_id values appeared exactly twice with identical values, including updated_at. Every duplicate had updated_at between 21:40 and 22:10 UTC on 2026-10-14; there were none before 21:40.
- SHP-88412907 had no row in shipments_fact before the run, so the conflicting key came from within the same batch.
- logistics-eng confirmed the restart at 22:10 and the resume from the 21:40 checkpoint.

## Inferred cause

- Proposed explanation: the connector replayed 30 minutes of change events after its restart, so shipments_raw (which does not enforce its key) received a second copy of each row changed in that window. transform_shipments did not deduplicate, and the plain INSERT failed on the first repeated key.
- Supporting observations: the duplicates are exact copies confined to the replay window, and the restart is confirmed by the owning team.
- Confidence: high that the replay produced these duplicates; medium that replays are the only way duplicates reach shipments_raw.
- Alternatives considered: rows left by an earlier partial attempt, the usual cause in runbook RB-006 (Duplicate key violation on load). Ruled out: there was a single attempt, it was rolled back, and the key was not in shipments_fact before. A join fanning out rows in the transform: ruled out, because the duplicates already existed in shipments_raw.

## Resolution and verification

- Actions: transform_shipments now keeps the row with the latest updated_at per shipment_id. load_shipments_fact now upserts (INSERT ... ON CONFLICT (shipment_id) DO UPDATE), as in RB-006. Deduplication is still needed, because Postgres cannot update the same row twice in one statement.
- Verification: the load succeeded at 02:58 with 47,312 rows, equal to the distinct count. shipments_fact has no repeated shipment_id. The 03:31 freshness check passed with shipments_fact 33 minutes old, and the daily close was published before 06:00.

## Prevention

- The shipments_raw schema doc now tells consumers to deduplicate on shipment_id.
- logistics-eng will announce connector restarts in #data-platform-oncall.
- Every load in shipments_sync is now idempotent (RB-006 prevention).
